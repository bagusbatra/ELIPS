## 3. Phase 5 — Tugas & Ujian (7 November 2026, `327ade8`)

### 3.1 Tujuan

Phase 5 melengkapi alur belajar v4.0 dari sisi penilaian non-ujian-tertulis: kelas dapat memiliki **tugas** dan **ujian**, peserta dapat mengumpulkan tugas dan menerima hasil ujian, sedangkan instruktur/Admin dapat menilai, meminta revisi, dan menutup periode penilaian. Implementasi bersifat aditif dan tetap memakai model kelas, kurikulum, serta enrollment yang sudah ada.

### 3.2 Model data

Sembilan tabel baru ditambahkan ke `api/schema.sql`:

| Tabel | Fungsi | Constraint utama |
|---|---|---|
| `assignments` | Definisi tugas per kelas | FK ke `classes`, `curriculum_versions`, `modules`, `lessons`, `users` |
| `assignment_files` | Lampiran/bahan tugas | FK `assignment_id` cascade |
| `assignment_rubrics` | Kriteria penilaian | FK `assignment_id` cascade; urutan `sort_order` |
| `submissions` | Pengumpulan tugas per enrollment | UNIQUE(`assignment_id`, `enrollment_id`); FK ke tugas, enrollment, peserta, penilai |
| `submission_files` | Berkas jawaban peserta | FK `submission_id` cascade |
| `submission_reviews` | Riwayat submit/nilai/revisi/terima | FK `submission_id` cascade; `reviewer_id` SET NULL |
| `exams` | Definisi ujian per kelas | FK ke `classes`, `curriculum_versions`, `users` |
| `exam_participants` | Daftar peserta ujian | UNIQUE(`exam_id`, `enrollment_id`) |
| `exam_results` | Nilai/status hasil ujian | UNIQUE(`exam_id`, `enrollment_id`); `graded_by` SET NULL |

Enum penting:

- `assignments.type`: `file_upload`, `text_submission`, `in_class_practice`, `external_reference`.
- `assignments.status` dan `exams.status`: `draft`, `published`, `closed`, `archived`.
- `submissions.status`: `submitted`, `late`, `reviewed`, `revision_requested`, `resubmitted`, `accepted`.
- `exam_participants.status`: `registered`, `attended`, `absent`, `excused`.
- `exam_results.status`: `not_assessed`, `excused`, `missing`, `graded`.

### 3.3 Backend dan API

Enam belas aksi baru:

- **Tugas:** `assignment.classroom`, `assignment.detail`, `assignment.create`, `assignment.update`, `assignment.status`, `assignment.delete`, `assignment.submit`, `assignment.review`, `assignment.submissions`.
- **Ujian:** `exam.classroom`, `exam.detail`, `exam.create`, `exam.update`, `exam.status`, `exam.delete`, `exam.result`.

Aturan server utama:

- Instruktur hanya dapat mengelola kelas yang diampu; peserta hanya melihat tugas/ujian dari enrollment miliknya.
- Tugas `in_class_practice` tidak dapat dikumpulkan secara daring.
- Tugas `file_upload` mewajibkan berkas bila `require_file` aktif; ekstensi dan ukuran divalidasi.
- Satu enrollment hanya memiliki satu baris `submissions` per tugas; pengumpulan ulang diizinkan sebelum diterima/review.
- Nilai tidak boleh melebihi `max_score`; permintaan revisi dan penerimaan tercatat di `submission_reviews` serta audit.
- `exam.result` menyimpan nilai/status hasil ujian; status `graded` mewajibkan nilai.
- Snapshot hanya mengirim metadata tugas/ujian dan tidak mengekspos `instructions`, jawaban teks peserta, maupun `file_path`.

### 3.4 Mode lokal

- Sembilan key baru: `elips_assignments`, `elips_assignmentFiles`, `elips_assignmentRubrics`, `elips_submissions`, `elips_submissionFiles`, `elips_submissionReviews`, `elips_exams`, `elips_examParticipants`, `elips_examResults`.

### 3.5 UI

- **Instruktur (`instructor/manage-course.html`):** panel **Tugas & Ujian** per kelas, modal tambah/ubah tugas (jenis, status, modul/pelajaran, jadwal buka/tenggat, nilai maksimum, bobot, aturan berkas, rubrik), modal pengumpulan untuk menilai/minta revisi/menerima, serta modal tambah/ubah ujian dan pengisian hasil.

## 4. Aksi Langsung Kalender & Filter Jadwal Lanjutan (9 November 2026, `476534b`)

### 4.1 Tujuan

Menjadikan `admin/schedule.html` sebagai pusat operasi sesi pertemuan, bukan sekadar tampilan baca, dengan filter yang lebih lengkap dan aksi langsung yang konsisten di mode server maupun `localStorage`, tanpa perubahan skema database.

### 4.2 Perubahan backend

- `session.status` menerima parameter opsional `reason`. Bila diisi, alasan ditambahkan ke `notes` sesi dan detail audit; status, JP aktual, dan guard kepemilikan tetap mengikuti aturan sebelumnya.
- Tidak ada perubahan `api/schema.sql`; alasan memakai kolom `notes` yang sudah ada.
- `session.create`, `session.update`, dan `session.delete` tetap memakai validasi/otorisasi server yang sama dengan halaman akademik.

### 4.3 Perubahan UI

- Filter baru: instruktur, lokasi, dan multi-status berbasis chip (Semua, Terjadwal, Terkonfirmasi, Selesai, Dijadwalkan Ulang, Dibatalkan, Tidak Hadir).
- Seluruh filter (cabang, kelas, instruktur, lokasi, status) berlaku untuk kalender bulanan, agenda harian, ringkasan JP, statistik, dan tabel sesi.
- Filter, bulan, dan tanggal aktif disinkronkan ke query string (`branch`, `class`, `instructor`, `location`, `status`, `month`, `date`) dan dipulihkan saat halaman dibuka kembali.
- Tombol **Tambah Sesi** pada header, sel kalender, dan agenda kosong membuka form dengan tanggal terisi otomatis.
- Modal detail sesi menyediakan aksi **Edit**, **Jadwalkan Ulang**, **Batalkan**, **Tandai Selesai**, dan **Hapus** sesuai status/presensi sesi.
- Form sesi memakai konvensi `admin/academic.html` (kelas, nomor pertemuan, tanggal, modul, waktu, lokasi/ruang, tentor, JP, status, catatan) dan menampilkan pemberitahuan khusus saat menjadwalkan ulang.
- Tabel sesi mendapat tombol aksi lihat/edit; tombol disembunyikan atau ditolak bila sesi sudah selesai atau berpresensi.

### 4.4 Aturan bisnis

- Aksi kalender tidak melewati aturan yang sudah ada: sesi `completed` tidak dapat dihapus/dijadwalkan ulang, sesi berpresensi tidak dapat dihapus, dan instruktur non-pengampu tetap ditolak server.
- Pembatalan bersifat opsional alasannya; bila diisi, alasan tersimpan di catatan sesi dan audit.
- Reschedule membuat sesi pengganti baru bertaut `rescheduledFromId` dan menandai sesi asal `rescheduled`; sesi asal tidak dihitung sebagai JP aktual.
- Menandai selesai mengisi JP aktual dari JP rencana bila masih kosong.
- Filter status kosong berarti semua status; memilih chip status menerapkan filter ke seluruh tampilan.

### 4.5 Pengujian

- `php -l api/actions.php` dan `node --check assets/js/crud-academic.js` lulus.
- `test-schedule-actions.js` lulus: filter instruktur/lokasi/multi-status, pembuatan sesi dari kalender, edit, reschedule, pembatalan beralasan, tandai selesai, hapus, sinkronisasi URL, dan pemulihan filter dari URL.
- Regresi UI `test-branch-pages`, `test-sessions-page`, `test-learning`, `test-instructor` lulus; regresi backend/lokal `api-phase5` 52/52, `api-v4-sessions` 37/37, `local-phase5` 34/34, `local-v4-sessions` 47/47.

### 4.6 Keterbatasan

- Belum ada drag-and-drop atau pengubahan tanggal langsung pada kalender; perubahan tanggal memakai form edit/reschedule.
- Aksi massal (mis. batalkan beberapa sesi sekaligus) belum tersedia.

## 5. Absensi Staf Berbasis Kamera (9–10 November 2026)

### 5.1 Fitur awal (`0ddf6dd`)

Absensi pada dashboard Admin adalah **absensi pribadi staf/admin yang sedang login**, bukan presensi peserta per sesi.

- **Backend:** tabel `staff_attendances` (tabel ke-23 saat itu) dengan identitas pengguna, jenis `in`/`out`, tanggal dan waktu, zona waktu, foto base64 + `photo_mime`, koordinat/akurasi, label & sumber lokasi, IP, user agent, platform, bahasa, layar, memori perangkat, CPU core, tipe koneksi, status online, catatan, dan timestamp. FK `user_id` memakai `ON DELETE CASCADE`; index per pengguna/tanggal, tanggal, dan waktu.
- **API:** `staffAttendance.create`, `staffAttendance.list`, `staffAttendance.delete`; hanya Admin dan hanya atas namanya sendiri.
- **Validasi server:** jenis absensi, tanggal (`checkdate`), `takenAt`, foto wajib data URL gambar valid (`getimagesizefromstring`), batas ukuran, koordinat berpasangan dan dalam rentang, serta pembatasan panjang metadata.
- **Privasi:** snapshot bootstrap tidak memuat koleksi/foto absensi; riwayat hanya dibaca lewat `staffAttendance.list`.
- **Client:** hero **Absensi Kehadiran**, kamera `getUserMedia` + pratinjau, Ambil Foto/Ulangi, fallback **Unggah Foto**, kompresi JPEG, riwayat pribadi, modal detail metadata, dan hapus dengan konfirmasi.
- **Mode lokal:** key `elips_staffAttendances`, aksesor `getStaffAttendances`/`setStaffAttendances`/`getStaffAttendancesByUser`, riwayat per pengguna dipangkas menjadi 20 catatan.
- **Audit:** entitas `staff_attendance`.

### 5.2 Penyempurnaan alur harian (`db2e0e1`, 10 November 2026)

- **Satu masuk + satu pulang per hari.** `allowedKind()` memfilter catatan berdasarkan tanggal lokal hari ini dan `userId` pengguna aktif. Hero hanya menampilkan:
  - **Absen Masuk** bila belum ada catatan `in` hari ini;
  - **Absen Pulang** bila `in` sudah ada dan `out` belum;
  - badge **Absensi hari ini lengkap** bila keduanya sudah tercatat;
  - tidak ada tombol aksi saat status lengkap, belum dimuat, atau gagal dimuat.
- **Modal kamera ringkas.** Hanya layar kamera, tombol **Ambil Foto**, **Ulangi**, **Nyalakan Kamera**, **Unggah Foto**, kolom **Catatan**, **Batal**, dan **Simpan Absensi**. Input tanggal/jam/lokasi manual dan panel metadata dihapus.
- **Penguncian otomatis saat simpan.** `attendanceDate` = tanggal lokal hari ini, `takenAt` = waktu simpan, koordinat GPS diambil saat modal dibuka atau dicoba ulang saat simpan. Pengguna tidak dapat mengubah tanggal/jam/lokasi.
- **Degradasi GPS.** Kegagalan GPS tidak memblokir absensi; `locationSource` menjadi `none`.
- **Modal berhasil.** Menampilkan foto, identitas akun (nama, email, role, ID), seluruh metadata absensi dan perangkat, serta hanya satu tombol **Selesai**. Modal tidak dapat ditutup dengan Escape/backdrop; setelah ditutup, riwayat dan status hero dimuat ulang.
- **Pengaman ganda.** Flag `saving` mencegah penyimpanan ganda; tombol dinonaktifkan selama proses; penutupan modal saat izin kamera masih menunggu ditangani.
- **Tanpa perubahan backend/skema.** Aturan harian ditegakkan di UI, bukan unique constraint database.

### 5.4 Keterbatasan absensi

- Aturan satu masuk/pulang per hari belum menjadi constraint database; pemanggilan API langsung masih dapat membuat duplikat.

- Belum ada koreksi/approval absensi oleh admin lain, rekap, atau kaitan payroll/jam kerja.

## 10. Rencana Selanjutnya

1. **Rekonsiliasi dokumentasi Phase 5:** tambahkan 9 entitas ke `erd.md`, entri `log.md` 7 November, bagian PRD tugas/ujian, serta perbaiki angka tabel/aksi/key menjadi 32/80/33.
2. **Penyempurnaan tugas & ujian:** upload berkas biner yang aman, aksi penilaian massal, bank soal/auto-grading, dan integrasi bobot ke nilai akhir.
3. **Integrasi penilaian:** hubungkan skor tugas/ujian ke `grades`, rekap, dan syarat sertifikat.
4. **Penyempurnaan absensi:** unique index/guard transaksional untuk aturan harian, reverse geocoding, rekap kehadiran, dan kaitan payroll/jam kerja.
5. **Kalender lanjutan:** drag-and-drop, aksi massal, ekspor iCal, dan pengingat otomatis.
6. **Hardening:** rate limiting login, CSRF token, HTTPS wajib, rotasi session ID.
7. **CI/CD:** jalankan seluruh suite lokal dan server pada setiap push, termasuk `api-phase5`, `local-phase5`, dan suite absensi.

## 11. Kesimpulan

Sejak laporan 6 November 2026, ELIPS LMS menyelesaikan **Phase 5 (tugas & ujian)**, menjadikan kalender Admin sebagai pusat operasi sesi, dan menambahkan **absensi staf berbasis kamera** dengan alur harian yang terkunci otomatis. Kode aktual kini mencakup **32 tabel MySQL, 80 aksi API, dan 33 key `localStorage`**, dengan seluruh suite pengujian yang relevan lulus.

Prioritas terdekat bukan penambahan fitur baru, melainkan **menutup utang dokumentasi Phase 5** agar ERD, PRD, dan log kembali konsisten dengan kode, lalu mengintegrasikan nilai tugas/ujian ke nilai akhir serta memperkuat aturan absensi di level database.
